# 技术决策记录（ADR）

记录重要技术决策及其原因。状态：已确定 / 初步确定 / 待确认 / 已废弃。

---

## D001 · 文档体系与权威来源

**日期：** 2026-11-20
**状态：** 已确定

**决策：** `Docs/` 是唯一持续维护的开发依据；`md/` 下源规划 V0.2 保持只读，作为需求来源。

**原因：** 避免两份文档同时演化产生矛盾。实现细节以 `Docs/` 为准，源规划只提供原始意图。

**影响：** 任何架构变化先更新 `Docs/`，再改代码。

---

## D002 · 大地图俯视 + 小场景横版带纵深

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- 大地图：俯视平面，部队在 XY 平面移动。
- 小场景：横版侧视，Y 轴表示前后纵深，单位可在 XY 平面移动，按 Y 排序。
- 攻击方向仅左右，默认朝左。

**原因：** 匹配源规划的左右攻击、部件化人体/马匹美术，同时保留阵型所需的纵深空间。纯横版会让方阵退化为一条线。

**影响：**

- 小场景单位需要 Y 排序与纵深移动。
- 攻击判定只需左右朝向。
- 大地图与战斗使用不同相机与坐标表现。

## D003 · 静态配置 Resource、运行时 RefCounted、存档 JSON

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- 静态配置：`Resource` + `.tres`（`Data/`）。
- 运行时实体：`RefCounted` 纯数据类。
- 存档：JSON（`user://saves/`）。

**原因：**

- Resource 提供编辑器编辑、类型安全与资源引用。
- RefCounted 不进入场景树，适合大量实体与显式生命周期。
- JSON 透明、易调试、方便迁移和外部工具处理。

**影响：**

- 配置资源脚本放 `Scripts/Config/`，数据文件放 `Data/`。
- 实体类必须实现 `to_dict/from_dict`，不持有节点引用。

---

## D004 · WorldContext + WorldSimulation 替代 WorldManager

**日期：** 2026-11-20
**状态：** 已确定

**决策：** 源规划的 `WorldManager` 拆为：

- `WorldContext`：会话级容器，持有管理器，跨场景常驻。
- `WorldSimulation`：消费 `world_tick`，按固定顺序推进世界。

**原因：** 容器与调度职责不同；战斗/小场景期间世界仍需运行，容器必须独立于场景存在。

**影响：** 所有世界管理器由 `WorldContext` 装配，不新增 Autoload。

---

## D005 · 世界时间固定步长 0.1 秒

**日期：** 2026-11-20
**状态：** 已确定

**决策：** `TimeManager` 每 0.1 游戏秒发出一次 `world_tick`；单帧最多补 10 次，超出丢弃累积。

**原因：** 世界逻辑与渲染帧率解耦，保证 NPC 移动/AI 行为稳定可复现；卡顿保护避免死亡螺旋。

**影响：** 世界系统只订阅 tick，不在 `_process` 里实现世界逻辑。

---

## D006 · 不使用 Engine.time_scale / get_tree().paused

**日期：** 2026-11-20
**状态：** 已确定

**决策：** 游戏暂停通过 `TimeManager` 的门控与暂停原因栈实现。

**原因：**

- 全局时间缩放会同时影响 UI 动画。
- `get_tree().paused` 会冻结 UI、加载动画和部分管理器。
- 世界模拟需要固定步长，而不是全局 delta 缩放。

**影响：** 所有需要暂停的功能必须使用 `push_pause/pop_pause`。

---

## D007 · 暂停原因栈

**日期：** 2026-11-20
**状态：** 已确定

**决策：** `TimeManager` 维护暂停原因集合，任一原因存在即暂停。

**原因：** 多个系统（面板、对话、小场景）可能同时要求暂停，布尔值会互相覆盖。

**影响：** 压入与移除必须成对；原因常量集中在 `TimeManager`。

---

## D008 · 战斗期间 WorldTime = 0.5

**日期：** 2026-11-20
**状态：** 初步确定

**决策：** 战斗期间世界以 0.5 倍速运行，由 `BattleManager.set_battle_mode` 控制；玩家显式暂停优先级更高。

**原因：** 保持世界持续运转，同时降低战斗期间的世界推进速度，接近源规划设计。

**影响：** 战斗结束必须关闭覆盖；读档/返回主菜单要清理该状态。

**更新（D028）：** 屏幕内战斗改为通过 `battle` 暂停原因冻结世界（WorldTime = 0）。
**更新（D079）：** 离屏 AI 对 AI 战斗保持世界正常倍率，每游戏小时结算一次，不再使用 0.5 倍速覆盖。

## D011 · ID 格式与计数器

**日期：** 2026-11-20
**状态：** 已确定

**决策：** `<PREFIX>_<6 位序号>`，由 `IdGenerator` 生成，计数器随存档保存，永不复用。

**原因：** 稳定引用实体；避免节点名/数组下标变化导致存档失效。

**影响：** 读档必须先恢复计数器；实体跨部队转移时 ID 不变。

## D024 · 实体注册、删除与成员转移的安全规则

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- `UnitManager.add_unit()` / `PartyManager.add_party()` 遇到已存在 ID 时拒绝注册，返回空字符串并 `push_error`，原实体不变。
- `UnitManager.remove_unit()` 拒绝删除 `current_party_id` 非空的单位，必须先经 `PartyManager.remove_member()`。
- `PartyManager.add_member()` 是转队的唯一入口：先完成部队/单位存在性与阵营校验，再从所有其他部队成员列表移除，最后加入目标部队并更新 `current_party_id`。
- 重复加入同一部队不重复写入；同一部队成员列表中的重复项会被归一化为一条。
- 本阶段要求单位与部队 `faction_id` 相等，跨阵营加入直接拒绝。
- `remove_party()` 清空所有指向该部队的 `current_party_id`，单位保留在 `UnitManager`。

**原因：** 保持“一个单位最多属于一支部队”和双向归属一致；避免重复 ID 静默覆盖与删除单位后留下悬空成员引用。

**影响：** 删除单位必须先处理归属；跨阵营招募需要未来新增专门接口，不能绕过 `add_member()`；`remove_unit` / `remove_party` 改为返回 `bool`。

## D025 · 读档后校验士兵-部队成员关系

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- `PartyManager.validate_membership_consistency()` 返回错误描述列表，检查：
  1. 每个成员 ID 都有对应 `UnitData`；
  2. 每个非空 `current_party_id` 都有对应 `PartyData`；
  3. 一个单位最多出现在一支部队的成员列表中；
  4. `current_party_id` 与所在部队成员列表双向一致（含同一列表内重复项）。
- `WorldContext.load_from_save_data()` 在两个仓储恢复完成后调用校验；失败时逐条 `push_error` 并返回 `false`。
- 本阶段不自动修复：无法确定原始数据意图时，保留读入状态并拒绝进入游戏，避免擅自改写存档。

**原因：** 两个管理器各自反序列化成功，不代表跨实体引用正确；静默修复可能掩盖存档损坏。

**影响：** 损坏成员关系的存档无法加载，需要后续显式迁移/修复工具；其他实体引用（阵营、地点、领主）尚未纳入同一校验入口。

---

## D026 · StatCalculator 作为属性初始化的唯一入口

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- `UnitManager.create_unit()` 只负责身份、配置引用、阵营、装备与注册；基础属性统一调用 `StatCalculator.apply_to_unit()`。
- 当前 `compute_final_stats()` 直接复制 `UnitConfig` 的 `base_max_hp` / `base_attack` / `attack_interval` / `move_speed` / `attack_range`。
- `apply_to_unit()` 写入属性缓存并只对 `current_hp` 做上限 clamp；出生满血由 `UnitManager` 显式设置。
- 等级成长与装备加成暂不实现，接口参数保留。

**原因：** 避免 `UnitManager` 与 `StatCalculator` 各维护一套属性规则，导致后续成长/装备系统接入时出现两套真实来源。

**影响：** 所有运行时属性重算必须经过 `StatCalculator`；新增属性先扩展该接口，再接入调用方。

---

## D027 · 战斗会话、场景与结算职责分离

**日期：** 2026-11-20
**状态：** 已确定

**决策：**

- `BattleManager.start_battle()` 只创建 `BattleSession`、校验部队、生成 `BattleUnitState`、锁定参战部队并压入战斗暂停；不切换场景。
- 大地图交互控制器创建会话后调用 `SceneManager` 进入 `BattleScene`。
- `BattleScene` 读取会话生成 `UnitActor`，逐帧驱动 `UnitController`；伤害只写 `BattleUnitState.battle_hp`，不修改 `UnitData` / `PartyData`。
- 玩家点击“返回大地图”时，`BattleScene` 调用 `BattleManager.finish_battle()` 完成统一结算，再由场景控制器切回 `WorldMap`。

**原因：** 数据结算与场景导航职责不同；把场景切换放进 `BattleManager` 会让会话逻辑依赖表现层，也降低可测试性。

**影响：** `start_battle` / `finish_battle` 不负责场景切换；`BattleManager` 是唯一的战斗结算写入口；场景节点不持有权威数据。

---

## D028 · 屏幕内战斗暂停世界时间

**日期：** 2026-11-20
**状态：** 已确定（替代 D008 的屏幕内 0.5 倍速方案）

**决策：**

- 屏幕内战斗通过 `TimeManager.push_pause(GameManager.PAUSE_REASON_BATTLE)` 冻结 WorldTime（有效倍率 0）。
- 战斗场景使用 `_physics_process` 独立推进，不受世界暂停影响。
- 战斗结束移除 `battle` 暂停原因，恢复进入战斗前的基础倍率与其他暂停原因。
- `TimeManager.set_battle_mode(0.5)` 作为历史接口保留；屏幕内战斗与当前离屏小时结算均不使用。
- 大地图对话使用 `ui_panel` 暂停；发起战斗时先压入 `battle`，再释放 `ui_panel`，避免中间帧恢复世界。

**原因：** Milestone 2 要求进入战斗时暂停大地图模拟；暂停原因栈能保留其他系统的暂停状态。

**影响：** `Time_System.md` 的屏幕内战斗时间改为 0；离屏战斗后来按 D079 保持正常倍率并每游戏小时结算，0.5 倍速方案未采用。

---

## D029 · 阵亡单位结算规则

**日期：** 2026-11-20

## D038 · 大地图遭遇由统一管理器判定，AI 只维护攻击意图

**日期：** 2026-11-21
**状态：** 已确定

**决策：**

- `PartyData.attack_intent` 是运行时字段，不进入存档；由 `AIManager` 在明确追击/拦截时设置。
- 攻击意图必须明确指向对方：`attack_intent == true` 且 `current_target_id == 对方 party_id`。
- `EncounterManager.update_encounters()` 是唯一遭遇判定入口，在移动之后、AI 决策之前执行
  （原实现位于 `WorldMapManager`，按 D040 迁移到独立管理器）：
  - 双方有效、非 DISABLED、成员非空、阵营敌对；
  - 距离 <= `AI_ENCOUNTER_RADIUS (50)`；
  - 至少一方的攻击意图指向对方。
- 满足条件后交由 `BattleManager`：
  - 双方未参战 → 创建离屏战斗；
  - 一方已在离屏战斗 → 检查另一方能否加入；
  - 玩家被主动拦截 → 停止双方、记录待处理遭遇并请求 WorldMap 弹出遭遇对话；
  - 已在同一战斗 / 不可加入 → 不重复创建。
- `WorldSimulation` 在存在待处理玩家遭遇时跳过该 tick 的 AI，避免对话展示前创建新战斗。
- AI 不再各自判断“距离够近就开战”，避免同一条件在多处使用不同距离。

**原因：** 双方同时移动时，单纯由追击方在自己的 AI 中判断距离会导致追逐循环；把遭遇判定集中到移动之后的世界层，可以使用双方实际位置和明确的意图状态，统一 AI 对 AI 与玩家拦截规则。

**影响：** 遭遇距离 50 可在一个常量调整；攻击意图不持久化，读档后由 AI 重新建立（KI336）。

## D040 · 新增 EncounterManager，区分强制遭遇与玩家中途参战

**决策：**

  - 玩家接近进行中的离屏战斗时的中途参战交互（`BATTLE_INTERACTION_RADIUS = 55`）；

- 两种玩家交互明确区分：
  - 敌对 AI 主动攻击玩家：`encounter_dialogue`（**更新：D080 增加“撤退”与玩家主动追击接触**）；
  - 玩家接近已发生的 NPC 战斗：`battle_encounter_dialogue`，提供“加入战斗/离开”。
- 玩家选择离开后，`EncounterManager` 记录 declined battle id；玩家仍在 90 世界单位退出范围内时不重复提示，离开范围后可重新触发。

- 战斗结束、ID 变化、玩家已参战或面板异常关闭时，WorldMap 清理本次交互暂停与待处理请求。
- 不改变存档 Schema；攻击意图、待处理遭遇、交互 ID 与拒绝记录均为运行时状态。

**原因：** 遭遇距离与战斗转换属于跨 AI 的公共规则，放在具体 AI 中会导致距离与状态不一致；玩家中途参战又需要 UI 决策，不能继续沿用自动加入。独立 `EncounterManager` 让检测、暂停与 UI 的职责边界清晰。

**影响：** 测试需覆盖加入/离开、拒绝后不重复、离开范围后重触发、战斗结束/异常清理与暂停原因栈。玩家加入后的战斗侧仍按阵营关系自动确定（KI331）。

**决策：**

- `FormationManager` 只计算相对队形槽位：
  - `INFANTRY_LINE`（横向，超过 5 列自动加深）；
  - `DEPTH`（纵深单列）；
  - `LOOSE`（更大间距网格）；
  - 方阵/弓手线/骑兵纵队保留扩展。
- `BattleScene` 负责部队层级：
  - 每 0.4 秒按战斗侧重算最近敌方侧与双方质心；
  - 两军在中点附近列阵，避免阵型中心互换；
  - 同侧多部队使用 `PARTY_LANE_SPACING` 分区；
  - 把世界坐标槽位写入 `UnitController.formation_slot`。
- `UnitController` 负责单位层级：
  - 走向自己的槽位；
  - 用局部分离力避免重叠；
  - 进入攻击范围后停止推进并攻击；
  - 目标死亡后由场景刷新槽位。
- 邻居缓存由 `BattleScene` 每 0.3 秒构建局部列表，禁止每个单位每帧扫描全场。
- 预留 `set_party_move_order()` / `set_party_formation()` 供未来键盘部队指令使用。

**原因：** 让每个单位自行追逐同一敌人会堆叠；部队级槽位能保持前后排与多部队区域，单位级避让负责局部间距。两层分工避免每个 Unit 重复计算整队队形。

**影响：** 当前是局部算法，没有寻路/地形阻挡（KI341）；高级阵型与冲锋留待后续。

## D079 · 离屏战斗按游戏小时结算伤亡

**日期：** 2026-11-21
**状态：** 已确定

**决策：**

- NPC 对 NPC 战斗不创建小地图场景，继续使用 `BattleSession` 数据模拟。
- 新增 `OffscreenBattleResolver` 与 `OffscreenBattleConfig`（默认 `Data/Combat/offscreen_battle_default.tres`）。
- 每累计 1 个游戏小时（6 世界秒）结算一次伤亡；屏幕战斗期间 `offscreen = false`，完全跳过。
- 单兵战力由攻击、最大生命、兵种等级（tier）、骑乘状态与剩余生命比例计算；战斗侧压力由敌方总战力占比决定；伤亡比例加入 ±30% 随机波动。
- 伤亡按小数累计，避免小部队每小时固定损失相同人数；战力较低的单位更可能阵亡。
- 一方全灭、平局或达到 48 小时安全上限时结束；结束统一走 `finish_battle()`。
- 玩家中途加入保留已有 `BattleUnitState` 伤亡与 HP，并把 `offscreen` 切换为 false；不会重复结算当前小时。

**原因：** 旧实现 10 世界秒后一次性确定性结算，无法体现人数、等级、骑乘、剩余战力与波动，也无法让玩家在世界时间中观察持续变化的战斗。小时结算复用现有 BattleSession/结算流程，不引入平行伤亡系统。

**影响：** 离屏战斗可能持续多个游戏小时；新增配置资源但不进入存档。每次小时结算后，阵亡单位立即从 `PartyData.member_unit_ids` 移除，`UnitData` 保留到最终结算，避免提前丢失战利品与阵亡事件；UI 同时通过 `BattleUnitState` 读取实时存活人数。
