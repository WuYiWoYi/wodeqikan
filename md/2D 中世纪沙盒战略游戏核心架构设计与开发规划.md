# 第一章：项目定位与核心设计原则

## 1.1 项目定位

本项目是一款以中世纪为背景的 2D 沙盒战略游戏。

玩家从一名普通角色开始，带领自己的小队在一个持续运转的开放世界中冒险。

随着游戏进程，玩家可以：
- 探索大地图。
- 招募士兵、训练部队。
- 与其他部队战斗。
- 进入村庄、城镇、城堡。
- 与 NPC 对话、接取任务。
- 进行交易、购买装备。
- 参与攻城与守城。
- 与其他领主建立关系。
- 建立自己的阵营。
- 招募其他领主及其部队。
- 指挥其他 NPC 部队进行战争。

游戏最核心的特点是：

**玩家并不是世界的唯一活动主体，整个世界拥有独立的模拟和运行机制。**

即使玩家不进行任何操作，其他 NPC 部队、领主及世界实体仍然会按照自己的规则活动。

## 1.2 核心架构原则

整个项目必须遵循以下原则。

### 原则一：大世界与小场景分离

游戏分为两个主要运行空间：

- 大地图：负责战略层面的世界模拟。
- 小地图：负责实际的角色操作和实时战斗。

两者通过统一的数据结构进行衔接。

### 原则二：数据与表现分离

所有重要游戏实体都必须有独立的数据。

例如：
- 士兵的数据不属于士兵场景。
- 部队的数据不属于大地图旗帜。
- 城镇的数据不属于城镇场景。
- AI 领主的数据不属于领主的显示节点。

场景节点只是数据的表现载体。

### 原则三：玩家与 AI 共用基础架构

玩家操控的角色、普通士兵、NPC 士兵尽量使用相同的 Unit 数据结构和基础表现架构。

玩家与 AI 的区别主要体现在控制方式和决策逻辑上。

### 原则四：统一时间管理

所有受到游戏时间影响的系统，都必须通过统一时间管理系统运行。

不允许各个系统自行定义时间倍率。

### 原则五：模块化与低耦合

各子系统拥有明确的职责和接口。

例如：
- Unit 不直接操作 PartyManager。
- BattleScene 不直接修改 WorldMap 场景节点。
- AI 不直接修改 UI。
- UI 不直接负责游戏规则结算。

系统之间通过数据、信号和明确的接口进行通信。

### 原则六：数据驱动

兵种、单位属性、装备、动画参数、AI 参数等尽可能使用配置数据定义。

避免将所有游戏数值直接写死在脚本中。

### 原则七：考虑长期扩展

初期只开发必要功能，但基础数据结构和接口必须考虑后续扩展。

例如，初期的 Party 只需要容纳士兵，但未来还要支持：
- 领主。
- 部队命令。
- 阵营归属。
- 军团组织。
- 部队之间的支援关系。

# 第二章：总体系统架构

## 2.1 架构分层

建议将整个游戏划分为六个逻辑层级。

| 层级 | 核心职责 |
|---|---|
| 全局管理层 | 游戏状态、时间、场景、存档 |
| 世界模拟层 | 大地图、世界实体、NPC 部队、领主 |
| 数据实体层 | Unit、Party、Lord、Settlement |
| 玩法逻辑层 | 移动、战斗、AI、编队、交互 |
| 场景表现层 | 大地图、小场景、角色动画、场景对象 |
| UI 交互层 | 主菜单、部队面板、对话、地点交互 |

这些是逻辑上的分层，不要求每一层都对应一个独立的 Godot 场景或节点。

## 2.2 核心系统列表

| 系统 | 主要职责 |
|---|---|
| GameManager | 游戏运行状态管理 |
| TimeManager | 游戏时间和时间倍率 |
| SceneManager | 场景加载和切换 |
| SaveManager | 存档读取和保存 |
| WorldManager | 世界实体和世界模拟调度 |
| WorldMapManager | 大地图坐标、移动、视野 |
| UnitManager | 单位数据及单位实例管理 |
| PartyManager | 部队数据和人员组织 |
| BattleManager | 战斗会话和战斗结算 |
| AIManager | AI 决策调度 |
| DialogueManager | 对话和分支选择 |
| UIManager | UI 界面管理 |

## 2.3 管理器之间的依赖关系

需要特别注意：

管理器不是越多越好，也不能让所有管理器都能够随意调用其他管理器。

建议采用以下依赖结构：

```text
GameManager
│
├── TimeManager
├── SceneManager
├── SaveManager
├── UIManager
│
└── WorldManager
    │
    ├── WorldMapManager
    ├── UnitManager
    ├── PartyManager
    └── AIManager

BattleManager
│
├── BattleSession
├── UnitManager
└── PartyManager

DialogueManager
```

以上表示逻辑职责和依赖方向，不要求严格按照节点树组织。

具体约束：

1. GameManager 负责游戏整体状态，不负责具体玩法。
2. TimeManager 不需要知道士兵或部队的具体逻辑。
3. WorldManager 负责调度世界模拟，不负责绘制大地图。
4. UnitManager 管理单位数据，不负责士兵 AI。
5. PartyManager 管理部队数据，不负责部队 AI。
6. AIManager 负责调度和决策，不直接负责单位表现。
7. BattleManager 负责战斗会话，不直接修改大地图节点。
8. UI 只负责展示和接收玩家输入，通过接口请求游戏逻辑执行。

## 2.4 Godot Autoload 规划

不建议把所有管理器都设置为 Autoload。

Autoload 过多容易导致全局依赖失控。

初期建议只设置以下全局节点：

| Autoload | 职责 |
|---|---|
| GameManager | 全局游戏状态 |
| TimeManager | 全局时间控制 |
| SceneManager | 场景切换 |
| SaveManager | 存档系统 |
| EventBus | 跨系统事件通信 |

WorldManager、BattleManager、UnitManager 等应由对应的游戏上下文创建和管理。

例如，WorldManager 可以在 WorldContext 中存在；BattleManager 可以由当前游戏上下文创建。

这样能够避免不同场景之间出现大量不必要的全局引用。

# 第三章：核心数据架构

这是整个项目最重要的基础。

## 3.1 实体数据与场景节点的区别

所有需要长期保存的实体，都必须拥有独立的数据对象。

例如：

```text
UnitData
    ↓
UnitController
    ↓
UnitVisual
```

其中：

UnitData：保存士兵数据。

UnitController：负责控制士兵在小场景中的行为。

UnitVisual：负责绘制士兵。

当士兵从小场景中消失时，UnitData 不应该因此消失。

同理：

```text
PartyData
    ↓
WorldPartyController
    ↓
PartyIcon
```

大地图旗帜只是 PartyData 的表现。

## 3.2 唯一 ID 系统

所有持久化实体都必须有唯一 ID。

建议格式：

| 实体 | ID 示例 |
|---|---|
| 士兵 | UNIT_000001 |
| 部队 | PARTY_000001 |
| 领主 | LORD_000001 |
| 地点 | SETTLEMENT_000001 |
| 阵营 | FACTION_000001 |
| 任务 | QUEST_000001 |

ID 不能依赖场景节点名称、节点路径或者数组索引。

一个士兵从玩家部队转移到其他领主部队时，UNIT_ID 不发生变化。

## 3.3 核心实体关系

```text
Faction
│
├── Lord
│   │
│   └── Party
│       │
│       └── Unit
│
├── Settlement
│
└── Other Parties

Player
│
└── Player Party
    │
    └── Unit
```

上述结构是逻辑关系示意。

玩家也可以作为一个独立的 Unit 存在，后续再根据需求建立 PlayerProfile 保存玩家专属数据。

## 3.4 数据归属规则

需要明确每类数据由谁负责。

| 数据 | 所属系统 |
|---|---|
| 士兵属性、装备、经验 | UnitData |
| 士兵所属部队 | UnitData / PartyData 关系 |
| 部队坐标、移动速度 | PartyData |
| 部队行动目标 | PartyData |
| 领主性格、决策状态 | LordData |
| 城镇人口、归属 | SettlementData |
| 阵营关系 | FactionData |
| 本次战斗临时状态 | BattleSession |
| 世界时间 | TimeManager |

尽量避免重复保存同一项权威数据。

例如，士兵的 current_party_id 应作为唯一的所属关系依据，不应该再让多个管理器分别维护互相独立的成员归属表。

# 第四章：游戏时间系统

## 4.1 时间管理目标

游戏具有两种主要运行模式：

- 大地图模式。
- 小场景模式。

大地图和小地图之间可能同时运行，因此需要区分不同时间域。

建议采用：

1. WorldTime：世界模拟时间。
2. SceneTime：小场景时间。
3. UITime：UI 表现时间。

## 4.2 大地图时间倍率

| 模式 | 时间倍率 |
|---|---:|
| 暂停 | 0 |
| 正常 | 1.0 |
| 二倍速 | 2.0 |
| 战斗期间 | 0.5 |

时间倍率由 TimeManager 统一控制。

大地图时间按钮及快捷键预留：
- 暂停。
- 正常速度。
- 二倍速。

## 4.3 不同状态的时间规则

| 状态 | WorldTime | SceneTime |
|---|---:|---:|
| 大地图正常 | 1.0 | 无 |
| 大地图暂停 | 0 | 无 |
| 部队管理面板 | 0 | 无 |
| 地点交互面板 | 0 | 无 |
| 大地图对话 | 0 | 无 |
| 小场景普通探索 | 0 | 1.0 |
| 小场景对话 | 0 | 1.0 |
| 小场景战斗 | 0.5 | 1.0 |

UI 动画使用独立的 UI 时间，不应因为游戏暂停而无法播放。

小场景对话时，玩家可以正常阅读和选择，但大地图世界继续以 0.5 倍速运行，除非后续设计明确修改该规则。

## 4.4 固定步长模拟

推荐采用固定时间步长模拟。

初期设定：

**世界模拟每 0.1 秒执行一次。**

即每秒执行 10 次世界模拟更新。

世界模拟使用累积时间：

```text
每帧：
    累积游戏时间

当累积时间 >= 0.1：
    执行一次世界模拟
    累积时间 -= 0.1
```

视觉表现仍然可以每帧更新。

这样可以将世界逻辑与渲染帧率分离。

需要注意：

- 固定步长主要用于世界模拟。
- 小场景物理与角色运动使用独立的物理更新机制。
- 不允许将渲染帧率直接作为世界时间。
- 不允许在每次渲染帧中重复执行昂贵的全局 AI 决策。

# 第五章：大地图系统

## 5.1 大地图基础实体

大地图包含：

- 玩家部队。
- AI 部队。
- 村庄。
- 城镇。
- 城堡。
- 其他特殊地点。

所有部队通过图标或旗帜表示。

所有地点通过地图标记表示。

## 5.2 部队移动

每个 PartyData 保存：

- world_position。
- target_position。
- movement_speed。
- current_order。
- movement_state。
- sight_range。

玩家点击地图后，设置目标坐标。

AI 部队由 AI 决策系统设置目标坐标。

WorldMapManager 负责统一处理部队移动。

大地图初期可以采用直线移动。

后续增加：
- 路径规划。
- 地形影响。
- 道路加成。
- 河流和山脉阻挡。
- 地图边界。

## 5.3 世界模拟与视觉表现分离

建议建立：

```text
WorldContext
│
├── WorldSimulation
│   ├── PartySimulation
│   ├── UnitSimulation
│   ├── AIManager
│   └── SettlementSimulation
│
└── WorldMapScene
    ├── MapBackground
    ├── PartyIcons
    ├── SettlementIcons
    └── WorldMapUI
```

WorldSimulation 负责数据更新。

WorldMapScene 负责显示。

例如，某个 AI 部队移动到新坐标：

1. 世界模拟更新 PartyData。
2. 发送位置更新事件。
3. 大地图图标读取最新坐标。
4. 更新视觉位置。

即使大地图场景暂时没有加载，世界数据仍然可以继续运行。

## 5.4 视野系统

所有部队都有圆形视野。

初期采用简单距离检测：

当两个部队之间的距离小于视野范围时，判定为发现。

需要记录：
- 当前可见部队。
- 新发现的部队。
- 已经离开视野的部队。

后续可以增加：
- 视野遮挡。
- 夜间视野。
- 天气影响。
- 侦察兵加成。

# 第六章：小场景系统

## 6.1 场景分类

小场景统一采用 2D 平面表达。

包括：

| 场景 | 主要用途 |
|---|---|
| BattleScene | 实时战斗 |
| VillageScene | 村庄探索 |
| TownScene | 城镇探索 |
| CastleScene | 城堡探索 |

## 6.2 场景基础架构

每个小场景采用统一的基础结构：

```text
GameplayScene
│
├── World
│   ├── Environment
│   ├── Characters
│   └── Interactables
│
├── Camera
├── SceneController
└── SceneUI
```

不同场景可以使用不同的 SceneController。

场景只负责当前空间的表现和操作。

不应该直接负责大地图实体的长期保存。

## 6.3 大小地图切换

进入小场景：

1. 记录当前世界状态。
2. 根据进入类型确定小场景。
3. 加载场景。
4. 根据数据生成角色和 NPC。
5. 开始小场景运行。

离开小场景：

1. 收集需要保留的变化。
2. 更新实体数据。
3. 释放小场景表现节点。
4. 返回大地图。
5. 恢复对应的世界时间状态。

# 第七章：士兵与角色系统

## 7.1 UnitData

所有士兵与玩家角色共用基础单位数据。

主要属性：

| 属性 | 说明 |
|---|---|
| unit_id | 唯一编号 |
| name | 名字 |
| level | 等级 |
| exp | 经验 |
| max_hp | 最大生命值 |
| current_hp | 当前生命值 |
| attack | 攻击力 |
| attack_interval | 攻击间隔 |
| move_speed | 移动速度 |
| attack_range | 攻击范围 |
| faction_id | 所属阵营 |
| equipment | 装备信息 |

## 7.2 一般信息

- 加入队伍时间。
- 招募来源。
- 招募地点。
- 原始阵营。
- 当前所属部队。

例如：

1900年1月从某村庄招募。

以上时间仅为示例，使用游戏内时间。

## 7.3 属性计算

等级提供单位基础属性。

装备提供额外属性。

建议将最终属性计算独立出来：

```text
最终属性
=
等级基础属性
+
装备属性
+
其他加成
```

不要直接把最终攻击力写回兵种配置文件。

## 7.4 UnitController

UnitController 负责：

- 移动。
- 加速度。
- 减速度。
- 朝向。
- 攻击。
- 受击。
- 死亡。
- 动画状态。

建议采用状态机：

```text
UnitController
│
├── Idle
├── Accelerating
├── Moving
├── Decelerating
├── Attacking
├── Hurt
└── Dead
```

骑兵与步兵共用移动逻辑，通过移动参数区分。

## 7.5 攻击系统

初期攻击流程：

1. 检测攻击范围。
2. 获取有效敌人。
3. 有多个目标时随机选择一个。
4. 判断攻击 CD。
5. 执行攻击动画。
6. 造成伤害。
7. 进入下一次攻击 CD。

单位默认朝左。

目标在右侧时朝右。

攻击方向初期只需要左右两个方向。

## 7.6 士兵美术层级

```text
Unit
│
├── UnitController
├── UnitVisual
│   ├── Shadow
│   ├── HorseVisual
│   │   ├── HorseHead
│   │   ├── HorseBody
│   │   ├── HorseLegs
│   │   └── Saddle
│   │
│   └── HumanVisual
│       ├── LeftFoot
│       ├── Body
│       ├── FactionCloak
│       ├── Head
│       ├── Helmet
│       ├── HelmetDecoration
│       ├── RightHandWeapon
│       └── LeftHandWeapon
│
└── AnimationController
```

实际绘制顺序需要允许调整 Z Index。

骑马与步行采用不同的美术组合。

不要求所有身体部件都拥有独立动画。

# 第八章：部队系统

## 8.1 PartyData

部队是大地图的基本移动实体。

每个部队由多个 Unit 组成。

主要数据：

- party_id。
- party_name。
- faction_id。
- world_position。
- movement_speed。
- sight_range。
- member_unit_ids。
- current_order。
- current_target。

## 8.2 部队移动速度

初期可以使用简单计算。

后续考虑：

- 部队最慢成员。
- 骑兵比例。
- 负重。
- 地形。
- 道路。
- 坐骑。

具体公式后续确定。

## 8.3 部队管理 UI

点击大地图部队按钮：

1. 暂停世界时间。
2. 打开部队管理面板。
3. 显示全部成员。
4. 显示属性。
5. 支持选择和查看士兵。
6. 支持人员编队。

## 8.4 编队系统

编队作为独立子系统。

负责定义：
- 编队类型。
- 编队成员。
- 站位。
- 队形参数。

预留：
- 步兵方阵。
- 步兵线阵。
- 弓箭手阵型。
- 骑兵阵型。

编队不直接负责士兵的具体攻击行为。

# 第九章：AI 战斗系统

## 9.1 单位 AI

使用 FSM 状态机。

初期行为：

- Idle。
- Move。
- Attack。
- Defend。
- Retreat。

后续扩展：

- Shield。
- Pursue。
- Protect。
- FormationMove。
- Charge。

## 9.2 部队 AI

负责一群士兵的集体行为。

```text
PartyAI
│
├── FormationManager
├── MovementOrder
├── AttackOrder
├── DefendOrder
└── RetreatOrder
```

部队 AI 下达命令。

单位 AI 负责具体执行。

例如：

PartyAI 下达攻击命令，UnitAI 负责寻找敌人并攻击。

## 9.3 AI 决策调度

AI 不需要每一帧都做决策。

建议区分：

- 单位实时行为。
- 部队战术决策。
- 领主战略决策。

不同层级采用不同更新频率。

这样可以控制大量 NPC 同时存在时的性能消耗。

# 第十一章：战斗会话与援军系统

这是整个项目最重要的跨场景系统。

## 11.1 BattleSession

每次战斗创建一个独立的 BattleSession。

BattleSession 保存：

- battle_id。
- 战斗地点。
- 参战部队。
- 参战单位。
- 战斗状态。
- 双方阵营。
- 援军列表。
- 战斗结果。

BattleSession 是本次战斗的临时数据容器。

它不替代原有的 UnitData 和 PartyData。

## 11.2 战斗初始化

```text
大地图遭遇
    ↓
BattleManager
    ↓
创建 BattleSession
    ↓
读取双方 PartyData
    ↓
生成参战 Unit
    ↓
加载 BattleScene
    ↓
开始战斗
```

## 11.3 战斗期间的世界模拟

战斗开始后：

- WorldTime = 0.5。
- SceneTime = 1.0。
- 大地图继续运行。
- 其他部队继续移动。
- AI 继续执行决策。

大地图上的参战部队需要进入战斗锁定状态。

**参战部队不能同时在大地图继续移动，又在小地图中进行战斗。**

因此需要建立 Party 的战斗状态：

- Available。
- InBattle。
- Returning。
- Disabled。

## 11.4 战斗支援

其他部队进入战斗区域时：

1. 检查距离。
2. 判断阵营。
3. 判断是否满足支援条件。
4. 判断是否允许加入战斗。
5. 将支援部队加入 BattleSession。
6. 在小地图中生成援军。

敌我双方采用相同机制。

支援系统需要考虑援军加入时的单位数据同步。

## 11.5 战斗数据权威性

战斗期间，参战单位的临时战斗状态由 BattleSession 持有。

例如：

- 战斗中的当前生命值。
- 临时战斗状态。
- 战斗内位置。
- 战斗内行为。

不能让 WorldSimulation 和 BattleScene 同时修改同一个单位的战斗生命值。

## 11.6 战斗结算

战斗结束：

1. 汇总所有参战单位。
2. 更新剩余生命值。
3. 记录死亡人员。
4. 更新经验。
5. 更新部队成员关系。
6. 更新战斗结果。
7. 更新双方部队状态。
8. 清理 BattleSession。
9. 返回大地图。

战斗结算必须由 BattleManager 统一执行。

# 第十三章：对话系统

## 13.1 DialogueManager

大地图和小地图共用同一套对话系统。

对话触发方式：

大地图：
- 接近 NPC。
- 接近其他部队。
- 触发对话。

小地图：
- 操控角色接近 NPC。
- 点击交互。

## 13.2 对话数据

采用节点式数据：

- dialogue_id。
- speaker。
- dialogue_text。
- choices。
- next_node。
- conditions。
- effects。

支持：
- 多分支。
- 条件判断。
- 任务触发。
- 好感度。
- 阵营关系。
- 招募。
- 谈判。

## 13.3 时间管理

大地图对话时暂停世界时间。

小地图对话时，小场景保持运行；如果处于普通探索，世界时间仍为 0。

所有时间规则由 GameManager 与 TimeManager 统一协调。

# 第十四章：主菜单与存档系统

## 14.1 主菜单

## 14.2 存档架构

建议使用统一的 SaveData。

保存：
- 游戏版本。
- 游戏时间。
- 世界状态。
- 玩家数据。
- 士兵数据。
- 部队数据。
- 领主数据。
- 地点数据。
- 阵营数据。
- 任务数据。
- 当前场景状态。

## 14.3 存档原则

1. 只保存持久化数据。
2. 不直接保存场景节点。
3. 使用唯一 ID 关联实体。
4. 具备版本号。
5. 支持未来数据迁移。
6. 保存前进行数据校验。

初期使用 JSON 即可。

后续如果数据量增大，再考虑二进制格式或数据库。

## 14.4 战斗期间存档

建议初期只允许在安全状态下存档。

战斗期间暂不支持存档。

这样可以避免需要序列化大量战斗实时状态。

后续如果需要战斗中存档，再为 BattleSession 增加完整的序列化能力。

# 第十六章：AI 记忆文件与持续开发规范

## 16.1 设计目标

项目需要建立一套 Markdown 记忆文件体系。

它既是策划文档，也是 AI 辅助开发时的项目上下文。

每次开始开发前，AI 应该先阅读总索引，再读取相关系统文档。

每次完成开发后，需要检查并更新相关文档。

## 16.2 文件职责

| 文件 | 职责 |
|---|---|
| 00_Project_Index.md | 总索引、架构概述、文件导航 |
| 01_Core_Architecture.md | 核心架构与依赖约束 |
| 02_Development_Roadmap.md | 开发阶段与任务顺序 |
| 03_Design_Conventions.md | 命名、代码和数据规范 |
| 04_Change_Log.md | 重要变更历史 |
| Current_Status.md | 当前实际开发进度 |
| Technical_Decisions.md | 重要技术决策及原因 |
| Known_Issues.md | 已知问题和待处理事项 |

## 16.3 每次开发前的强制流程

1. 阅读 00_Project_Index.md。
2. 确认当前开发进度。
3. 根据任务读取对应子系统文档。
4. 阅读相关技术决策。
5. 检查现有代码。
6. 制定本次开发方案。
7. 开始开发。

## 16.4 每次开发后的强制流程

1. 更新实际开发状态。
2. 更新对应子系统文档。
3. 记录重要架构变化。
4. 记录新增接口和数据结构。
5. 记录已知问题。
6. 更新变更日志。
7. 检查总索引是否需要调整。

不能只记录开发结果，还要记录重要设计原因。

## 16.5 文档冲突处理

如果新开发需求与旧文档存在冲突：

1. 找出原有设计。
2. 明确本次修改的原因。
3. 确认是否会影响其他系统。
4. 更新相关文档。
5. 更新技术决策记录。
6. 删除或标记已经失效的旧规则。

禁止让不同 Markdown 文件长期保存互相矛盾的设计。
